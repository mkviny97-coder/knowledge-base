WORKFLOW DE SKILLS PARA AGENTES DE IA DO PROJETO
================================================================================

O projeto utiliza o framework ECC (Everything Claude Code) com skills organizadas
em 5 fases sequenciais. Cada fase possui skills especificas que os agentes
devem invocar via slash commands.

--------------------------------------------------------------------------------
1. FASE DE PLANEJAMENTO (O ARQUITETO)
--------------------------------------------------------------------------------
NUNCA deixe a IA comecar a escrever codigo sem antes passar por aqui.

* `/ecc:plan` → Para criar um plano de implementacao simples e direto.
* `/ecc:blueprint` → Para projetos complexos. Cria mapa tecnico detalhado,
  define arquitetura e dependencias.
* `/ecc:architecture-decision-records` → Para registrar por que uma decisao
  tecnica foi tomada (essencial para projetos que crescem).

--------------------------------------------------------------------------------
2. FASE DE IMPLEMENTACAO (O DESENVOLVEDOR)
--------------------------------------------------------------------------------
Onde o codigo nasce. Garantir codigo profissional.

* `/ecc:prp-implement` → A skill "Ouro". Implementacao profissional com rigor
  tecnico, evitando codigo "preguicoso".
* `/ecc:feature-dev` → Para adicionar funcionalidade nova em projeto existente.
* `/ecc:tdd-workflow` → Test-Driven Development. Forca a IA a escrever testes
  ANTES do codigo, garantindo que a funcao realmente funcione.

--------------------------------------------------------------------------------
3. FASE DE REVISAO E QUALIDADE (O QA/REVIEWER)
--------------------------------------------------------------------------------
Essencial para evitar bugs em producao. Chamar APOS o codigo ser escrito.

* `/ecc:code-review` → Revisao padrao: busca bugs, performance, padronizacao.
* `/ecc:orch-review` → Revisao "adversaria" e profunda. Multiplos especialistas
  discutem o codigo para achar falhas ocultas.
* `/ecc:verification-loop` → O "check final". Roda build, lint, testes e
  seguranca para dar veredito PASS ou FAIL.

--------------------------------------------------------------------------------
4. FASE DE MANUTENCAO E CORRECAO (O DEBUGGER)
--------------------------------------------------------------------------------
Para quando algo quebra ou o codigo ficou "sujo".

* `/ecc:build-fix` → Quando codigo nao compila ou da erro de TypeScript/
  Dependencias. Foca em consertar com menor alteracao possivel.
* `/ecc:refactor-clean` → Remover "codigo morto" (funcoes nao usadas) e
  simplificar estrutura sem mudar comportamento.

--------------------------------------------------------------------------------
5. FASE DE INFRAESTRUTURA E ENTREGA (O DEVOPS)
--------------------------------------------------------------------------------
Para tirar o codigo da maquina e colocar no ar.

* `/ecc:deployment-patterns` → CI/CD, Docker, estrategias de deploy.
* `/ecc:terraform-patterns` → Criar servidores na nuvem (AWS, Azure, GCP)
  via codigo (Infrastructure as Code).

--------------------------------------------------------------------------------
COMBO PERFEITO - SEQUENCIA EXATA PARA QUALQUER TAREFA
--------------------------------------------------------------------------------
Para resultado maximo, chame os agentes nesta sequencia:

1. PLANEJAR: `/ecc:blueprint` → (Aprove o plano gerado)
2. CODAR:    `/ecc:prp-implement` → (Gere o codigo)
3. REVISAR:  `/ecc:code-review` → (Corrija pontos apontados)
4. VALIDAR:  `/ecc:verification-loop` → (Confirme que tudo esta verde)

COMO OS AGENTES DEVEM USAR ESTAS SKILLS NA PRATICA
--------------------------------------------------------------------------------

EXEMPLO 1 - Nova funcionalidade em projeto React existente:
1. Agente Arquiteto: `/ecc:feature-dev` (entende o codebase) → `/ecc:plan` (plano)
2. Agente Dev: `/ecc:react-patterns` + `/ecc:prp-implement` (implementa)
3. Agente QA: `/ecc:code-review` → `/ecc:verification-loop`
4. Se falhar build: Agente Debugger: `/ecc:build-fix`

EXEMPLO 2 - Novo microservico Go do zero:
1. Arquiteto: `/ecc:blueprint` (arquitetura completa) → ADR via `/ecc:architecture-decision-records`
2. Dev: `/ecc:go-patterns` + `/ecc:prp-implement` (codigo + testes via `/ecc:tdd-workflow`)
3. QA: `/ecc:orch-review` (revisao profunda) → `/ecc:verification-loop`
4. DevOps: `/ecc:deployment-patterns` (Docker, CI/CD) → `/ecc:terraform-patterns` (infra)

EXEMPLO 3 - Refatoracao de legacy Python:
1. Arquiteto: `/ecc:plan` (escopo da refatoracao)
2. Dev: `/ecc:python-patterns` + `/ecc:prp-implement` (codigo novo)
3. Debugger: `/ecc:refactor-clean` (remove dead code)
4. QA: `/ecc:code-review` → `/ecc:verification-loop`

EXEMPLO 4 - Bug critico em producao:
1. Debugger: `/ecc:build-fix` (se erro de build) ou analise manual
2. Dev: `/ecc:prp-implement` (fix com teste via `/ecc:tdd-workflow`)
3. QA: `/ecc:verification-loop` (valida fix)
4. DevOps: `/ecc:deployment-patterns` (hotfix deploy)

--------------------------------------------------------------------------------
REGRAS DE OURO PARA OS AGENTES
--------------------------------------------------------------------------------
1. NUNCA pule a fase de planejamento. Sem plano aprovado, nao ha codigo.
2. SEMPRE use `/ecc:prp-implement` para codigo de producao (nao `/ecc:plan` sozinho).
3. SEMPRE rode `/ecc:verification-loop` antes de considerar tarefa completa.
4. SEMPRE invoque skill de linguagem especifica junto com implementacao.
5. Para revisao critica: use `/ecc:orch-review` (adversarial) em vez de `/ecc:code-review`.
6. Registre decisoes arquiteturais com `/ecc:architecture-decision-records`.
7. Mantenha ADRs atualizados - sao memoria do projeto.
8. Se codigo nao compila: `/ecc:build-fix` primeiro, so depois revisao.
9. Periodicamente: `/ecc:refactor-clean` para evitar debt tecnico.
10. Documente o "porque" nas ADRs, nao so o "o que".
